# Twoo's Treat Temple (repo: gf-drinks)

An iPhone home-screen web app (PWA) listing food and drinks with **no gluten ingredients** at UK restaurants and coffee shops, built from each restaurant's published allergen guide. Used by someone with coeliac disease, so accuracy beats completeness. Live at https://t-800isinevitable.github.io/gf-drinks/

## How it fits together

- `restaurants/<id>/restaurant.json` names a **reader** (`tools/adapters/<reader>.py`), or several as `"readers": [...]` merged into one menu (Starbucks drinks + food), plus display details, `tips`, `headline` (the one tip shown once the tips fold away after a page's first visit; required with tips, under 60 characters, and taken from the tips, never new advice), `gaps` (what the guide doesn't tell a coeliac) and `recheckDays`.
- When a reader decides an item itself because the guide wasn't plain (blank allergen column, sources disagreeing, versions under different names), it also sets the item's `decided`: one plain-English sentence the app shows on the item ("How the app decided") and in the Warnings sheet. The raw `warnings` strings are for the build log only.
- Readers: `starbucks_uk_pdf`, `starbucks_uk_food_pdf`, `pret_uk_pdf`, `five_guys_uk_pdf`, `pho_uk_pdf`, `blank_street_uk_pdf` (automatic, from PDFs in `guides/`; newest edition wins) and `manual_csv` (hand-kept `menu.csv`, see `restaurants/_template/`; used for Knoops).
- `tools/adapters/notices.py` extracts each guide's own warnings word for word for the Warnings page, including an "accreditation" kind for a guide's own gluten free claim.
- `tools/build.py` builds `site/data/restaurants.json` and `site/data/r/<id>.json`; `tools/check.py` validates. `site/data/` is generated, not committed.
- `tools/fetch_previous.py` downloads the live menus into `.previous/`; `tools/changes.py` then records what changed in each new guide ("changes"), carried forward until the next guide. The app shows it (a dismissable "what's new" banner, plus a lasting "What changed" link in Warnings and Help so it stays reopenable), and warns about favourites that are now to avoid or gone, in full on that restaurant's own page and on All, and as a short line elsewhere. A download failure here stops the build (`SystemExit`) rather than publishing with every restaurant's changes silently dropped; a 404 (nothing published yet) is treated as the first deploy, not a failure.
- `tools/snapshot.py` compares each menu with `tests/snapshots/<id>.txt` (same guide only); `tools/ui_check.py` drives the app in Playwright at iPhone size, light and dark; `tests/` has unit tests. `.github/workflows/checks.yml` runs all of it on pull requests; `guide-reminders.yml` opens an issue for guides ending within three weeks.
- `site/` is the app: `index.html`, `app.js`, `styles.css`, `sw.js` (offline, network-first; bump `CACHE` when shell files change), `manifest.webmanifest`, `phrases.json` (coeliac card), `cities.json` (hand-checked places in other cities, shown when the header switch is on that city instead of UK; validated by `check.py`, re-check reminders from `reminders.py`).
- Berlin places come from the berlin-glutenfrei.de list (Berlin contacts of the German Coeliac Society), each checked against the place's own website. Include only places that say everything is gluten free, or that have a separate gluten free kitchen. Their claims are quoted (with the app's translation), never adopted. Tag each place by who makes the claim (`claim`: place-all, list-all, place-part, separate). Put oats or wheat starch in `caution` with a row `flag`, and mark anything not confirmed open as `unconfirmed`. A green tag only for a place's own all-gluten-free claim with no caution. Opening `hours` (Mon to Sun) only from the place's own website; leave them out rather than guess. Search covers name, type, description and area, not street names.
- `.github/workflows/publish.yml` builds, checks and deploys to GitHub Pages on every push to `main` (pushes touching only `inbox/` are ignored).
- The app's Add menu button uploads to `inbox/` on the **`uploads` branch**, never `main`, all of an upload's files in one commit through GitHub's Git Data API (blobs, tree, commit, then moving the branch), so an upload arrives whole or not at all. A retry reuses the same folder and files, so a retry after a lost answer adds nothing. A daily scheduled Claude task follows `tools/SCAN_INSTRUCTIONS.md` and opens a pull request to `main` per upload for the owner to approve.
- `main` is protected: pull request with the `check` job passing, admins included, no force pushes. So every change, including the owner's guide uploads on github.com, goes through a pull request. `checks.yml` has no `paths-ignore`, because a required check that's skipped blocks merging.
- `.github/workflows/keep-alive.yml` re-enables the scheduled workflows monthly through the API (GitHub switches them off after 60 days with no activity); it commits nothing, so it works with `main` protected. The daily scan also checks their state (step 0 of `SCAN_INSTRUCTIONS.md`).
- `index.html` has a Content Security Policy `<meta>` tag. The inline theme script it allows by its hash must keep this hash in step: if that script's text changes, recompute the sha256 (base64) and update the `script-src` value, or the app breaks for everyone with no visible error until the console is checked. Anything new that loads a `blob:`, `data:` or outside URL needs the policy updated too: photos for upload are read through `blob:` URLs. Playwright's `wait_for_function` uses `eval`, which the policy blocks; use `wait_for_selector`.
- An upload's GitHub key (`app.js`, `KEY_KEY`) is removed from the phone, with a clear message, on a 401, or a 403 that isn't GitHub's rate limit: that means the key no longer works, not that the connection failed.
- `ui_check.py` runs everything in Chromium, then loads every page and uploads again in WebKit (the iPhone's engine). Upload checks run against `FakeGitHub`, an in-memory Git Data API, with the service worker blocked (in WebKit, requests from a page it controls get past `page.route`).

## Gluten rules (don't loosen these)

- Gluten = wheat, rye, barley, **oats**, spelt, kamut, or "gluten"/malt, as the guide marks them. Oats count because the guides list them as gluten cereals.
- When two sources in a guide disagree (e.g. allergen column vs ingredients), treat the item as containing gluten and record a warning.
- A row that isn't a dish to order (a part such as Five Guys' meat and toppings, or an ingredient listed on its own such as Blank Street's milks) gets a `roles` entry in `restaurant.json`: no staff card, and ingredients aren't shown as green. No name may be on both the list and the Avoid list (`check.py`); use `rename` (Five Guys' sausage is "Hot dog sausage", because its menu Hot Dog comes in a wheat bun).
- Five Guys "1" (not suitable due to preparation) in the gluten column = Avoid, with the reason shown.
- "May contain" gluten or oats (Blank Street's "May Contain" lines, Knoops' "MCT") = Avoid, with the reason shown. Gluten free oats still count as oats.
- Never call anything "gluten free". Say "no gluten ingredients". Pho is the exception that makes a claim (Coeliac UK accredited): quote its words, don't adopt them. The other guides make no gluten free claim.
- `ui_check.py` holds the app to this: any sentence of its own (pages, sheets, data such as tips and section names) that says "gluten free" must say whose claim it is ("says", "calls", "listed as"…). Someone else's words go in a `blockquote` or an element with `data-quote`.
- Where the app adds its own caution to a restaurant's data (for example Knoops' cannoli), label it as the app's, not the restaurant's. If the caution means the item may contain gluten, it goes on the Avoid list (`doubt` in a hand-kept `menu.csv`), not on the green list with a note.
- Readers must fail the build (`SystemExit`) rather than publish if the layout looks different (missing headings, unmatched marks, too few rows). A failed build keeps the previous live menus.
- Quote restaurant warnings word for word; don't paraphrase them as if they were the restaurant's words.

## Working conventions

- Amber (`--swap`) means "this item needs a change": the Swap and Ask tags, and a Berlin place with a caution. Banners and notes are neutral (surface colour, a small ⓘ). Item tags sit under the name and mustn't wrap, and the status buttons stay one even row, in the phone's font and a wide one; `ui_check.py` measures both. Item names are tidied by `build.py` (`CAPS_WORDS` lists the real capitals), by case only, so a saved favourite still matches.
- Accessibility (enforced by `ui_check.py`): font sizes in rem so iPhone Larger Text works, tap targets at least 44pt, text contrast at least 4.5:1 (no fading with opacity), VoiceOver-only words in a `.vh` span rather than `aria-label` on plain spans.
- **British English, no em-dashes**, plain warm wording in anything user-facing (app text, README, PR descriptions).
- Changes go through a branch and pull request, then merge once the check passes (`main` is protected); the publish workflow deploys from `main`.
- Before publishing: `pip install -r tools/requirements.txt -r tools/requirements-dev.txt`, then `python tools/build.py && python tools/check.py && python tools/snapshot.py && python tools/ui_check.py` (the last needs `python -m playwright install chromium webkit` once). `ui_check.py --shots DIR` saves screenshots to look at.
- When a reader's output changes on purpose, check the snapshot diff against the guide, then `python tools/snapshot.py --update`. Never update snapshots just to make the check pass.
- When adding a restaurant from a new PDF layout, write a reader, compare its output row by row against the rendered pages, and add a cross-check between the guide's own sources where possible. Make the reader stop the build on anything it can't place (stray marks, two drinks run together).
- Verify facts before stating them; label educated guesses as guesses.

## Known gaps

- Hotel Chocolat publishes no café allergen guide online; add it from photos of the in-café information via the app's Add menu.
- Knoops' newest guide is from March 2024, so it shows as possibly out of date.
- Not yet tested on a real device: installing, in-app upload with a real GitHub key, the first daily scan of a real menu, the reminder workflow's first issue. The German coeliac card hasn't been checked by a native speaker.
